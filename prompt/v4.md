# Problem-Solving App — Prototype Brief (v4)

> v4 supersedes v3. It folds in the decisions made while grilling v3: **Stage** is the
> canonical term, the deliverables are **only the pipeline and the web app** (no authored
> Two Sum unit), `content/` lives under `app/`, progress is **`localStorage`-only** (the
> `.progress` file is gone), and a small **Player Sandbox** fixture unit ships so the player
> is runnable.

## The idea

Build a prototype for a **Duolingo-style mobile learning app that teaches problem-solving**. Instead of writing code, the learner progresses by answering small, interactive questions that build understanding of a problem: how to solve it, how to evolve from a brute-force solution to optimized ones, the trade-offs involved, and how to recognize similar problems.

The prototype has two parts:

1. A **content pipeline** that turns a problem (from NeetCode) into structured learning content.
2. A **vanilla web app** that plays that content in a game-like, mobile-first way.

## Vocabulary

- **Section** — a NeetCode topic (e.g. *Arrays & Hashing*), shown as a group of units.
- **Unit** — a single NeetCode problem (e.g. *Two Sum*), containing exactly six ordered stages.
- **Lesson** — one interactive screen that teaches or checks a single idea.
- **Stage** — the pedagogical step a lesson belongs to, one of `Intro`, `BruteForce`, `Insight`, `Optimize`, `Tradeoff`, or `Recognize`. (Never "Chapter" or "step" — a *step* is a draggable item in `order-steps`.)
- **Interaction type** — the rendering and grading shape of a lesson. One of: `info`, `single-choice`, `multi-choice`, or `order-steps`.
- **Supportive visual** — a self-contained interactive HTML file attached to a lesson or, when useful, to an individual option or step. It helps the learner *see* rather than read.
- **Visualizing area** — the region of the lesson player that hosts the current supportive visual.

## What completing a unit proves

A finished unit must prove three things:

1. The learner **can solve** this particular problem.
2. The learner **understands the technique/pattern** and can recognize similar problems.
3. The learner understands the **evolution from brute force to optimized solutions** and the trade-offs between them.

## Unit structure: the fixed stage ladder

Every unit contains exactly six stages in this order:

`Intro → BruteForce → Insight → Optimize → Tradeoff → Recognize`

- **`Intro`** — understand the problem.
- **`BruteForce`** — build the naive idea.
- **`Insight`** — discover the key realization or pattern.
- **`Optimize`** — build the improved solution.
- **`Tradeoff`** — compare the solutions.
- **`Recognize`** — spot sibling problems.

Each stage contains **one to three lessons**, depending on what that stage needs to teach or check, so the number of lessons varies by unit — **at least six** (one per stage) and at most eighteen.

This maps onto the three proofs (`Intro` + `BruteForce` → proof 1, `Insight` + `Recognize` → proof 2, `Optimize` + `Tradeoff` → proof 3) while giving authors room to spend more than one lesson on a difficult stage.

## Interactive lessons

Questions must be **interactive**, favoring seeing over reading. Two rules:

1. **Visualize-on-select** — tapping an option selects it and, if the option has a supportive visual, loads that visual in the visualizing area. Selection is not submission; the learner submits with a separate **Check** button.
2. Prefer visualization over text wherever an idea can be shown.

For `single-choice`, tapping another option replaces the selection and its visual; an option without a visual restores the lesson's default. For `multi-choice`, tapping toggles an option. The visualizing area shows the visual for the most recently selected option that has one; when that option is deselected, it falls back to the most recently selected remaining option with a visual, or to the lesson's default visual when none remain.

### Interaction types (closed set of four)

The app renders every lesson from a fixed menu of four interaction shapes. Each lesson declares its `type`:

- **`info`** — a teaching screen with a title, body, optional supportive visual, and Continue button. No question.
- **`single-choice`** — select exactly one option, then check it.
- **`multi-choice`** — select all applicable options, then check them.
- **`order-steps`** — arrange scrambled steps into the correct order, then check the order. Reordering is **tap-based** (per-step up/down controls), never native drag-and-drop. Tapping a step that has a visual loads it without changing the step order.

### Lesson completion

- An `info` lesson is completed when the learner presses **Continue**.
- For a graded lesson, **Check** is enabled only when the answer is valid: one option for `single-choice`, at least one option for `multi-choice`, and all steps placed for `order-steps`.
- The state transition is **Check → incorrect feedback and retry**, or **Check → correct feedback → Continue → lesson complete**.
- Incorrect feedback is **generic** ("Not quite — try again"): it never reveals which items are wrong, and the current selection/order persists so the learner can adjust and re-check. The lesson's `explanation` is shown **only on a correct answer**, before Continue is revealed.
- Correctness is determined only by the lesson's answer data: option `correct` flags for choice lessons and the `answer` sequence for `order-steps`.
- A stage is complete when all its lessons are complete.
- A unit is complete when all lessons in all six stages are complete. Completing a unit unlocks the next available unit in its section.

### Supportive visuals

- **Every lesson, regardless of type, may declare its own supportive visual**, shown in the visualizing area. This is the primary way a lesson favors seeing over reading.
- **Additionally**, options in `single-choice` and `multi-choice`, and steps in `order-steps`, may each carry an optional supportive visual. Author one only when selecting or tapping it reveals something worth seeing.
- Visual paths are relative to the lesson folder. An omitted `visual` means no visual at that attachment point.
- A supportive visual is **fully self-contained** and loaded in an **`<iframe sandbox="allow-scripts">`**. It carries its own interactions, never communicates with the app, and does not depend on app state or the parent DOM.
- There is no app-native declarative visual renderer and no message protocol between app and visual.

## Part 1 — the content pipeline

The pipeline consists of **offline authoring skills** written in Markdown, not a runtime service. It takes a **hand-supplied problem spec** (problem title/slug, statement, and canonical solutions) and emits a **unit folder** named after the problem. A problem URL may be supplied only as an identifier; the pipeline performs no scraping.

The pipeline is delivered as **three pure-Markdown skills** under `.agents/skills/` — `extract-spec`, `author-unit`, and `author-lesson` — each with `name` + `description` frontmatter. They contain **no runtime code**.

Authoring is intentionally split across sessions:

1. The user invokes **`author-unit`** with the problem spec.
2. `author-unit` invokes **`extract-spec`** to normalize the supplied problem.
3. `author-unit` designs the six-stage ladder. For every stage, it proposes one to three lessons and gives each lesson an interaction type, a purpose, and a short description of its likely content.
4. `author-unit` shows the complete ladder to the user and waits. It must not write unit content before the user approves the ladder.
5. If the user comments, `author-unit` revises the ladder and asks again. Once the user approves it, `author-unit` writes the authoritative plan to `unit-plan.md`, creates the structural `unit.json`, and adds the unit to the top-level content manifest with `"available": false`.
6. In separate sessions, the user invokes **`author-lesson`** for each planned lesson. `author-lesson` reads `unit-plan.md`, designs the lesson and any useful lesson-level, per-option, or per-step supportive visuals, then writes the lesson files.
7. After writing a lesson, `author-lesson` checks the approved plan. When every planned lesson exists, it changes the unit's manifest entry to `"available": true`.

All generated content is committed to the repo as static files. The web app makes no runtime LLM calls.

## Part 2 — the web app

A **vanilla, zero-dependency, zero-build** app: **one `index.html` + one `app.js` + one `styles.css`**.

Because the app fetches JSON and HTML content, it runs from a local static HTTP server rather than directly from `file://`. The **web root is the `app/` folder** (`cd app && python3 -m http.server`); everything the app touches lives under `app/`. Serving the folder is an environment requirement, not an application backend.

- **Mobile-first only** — fixed mobile viewport (max-width ~430px, centered). No desktop view.
- Fetches the content manifest and draws a **Duolingo-style section tree** with locked/unlocked units.
- Opening a unit lazy-loads its `unit.json`, then plays its stages and lessons in order (a **lesson player**).
- **Navigation & state**: a single **in-memory state object** with a top-level `render()` that redraws the DOM on change, plus an in-app **Back** control. There is **no hash router**; a reload starts at the home tree.
- **Progression**: units in a section unlock linearly as earlier ones are completed (unit completion is defined under *Lesson completion*).
- **Progress store**: progress is persisted in the browser's **`localStorage`** only. There is **no `.progress` file**. On each lesson completion the app writes the updated completions to `localStorage`; on load, effective progress is read back from `localStorage` (empty on a fresh browser). An in-app **"Reset progress"** control clears `localStorage`.
- No accounts, runtime backend, streaks, hearts, or XP.

The content manifest owns only authoring availability. It does not store progression locks. A unit with `"available": false` is an unimplemented stub and always locked; available units are locked or unlocked from their order and the current progress.

## Content layout

```
app/
  index.html
  app.js
  styles.css
  content/
    index.json                   ← manifest: sections → ordered units
    player-sandbox/              ← dev fixture unit (see Scope)
      unit.json
      ...
```

Authored units (produced by the pipeline) follow this shape inside `content/`:

```
content/
  <problem-slug>/                ← a unit folder
    unit-plan.md                 ← approved stage and lesson design
    unit.json                    ← unit metadata + ordered lessons (each tagged with its stage)
    01-intro/
      01-understand-the-problem/
        lesson.json
        overview.html            ← optional supportive visual(s)
    02-brute-force/
      01-enumerate-pairs/
        lesson.json
        pair-scan.html
    ...
```

### `content/index.json`

```json
{
  "sections": [
    {
      "id": "arrays-hashing",
      "title": "Arrays & Hashing",
      "units": [
        { "id": "player-sandbox", "title": "Player Sandbox", "path": "player-sandbox", "available": true },
        { "id": "two-sum", "title": "Two Sum", "path": "two-sum", "available": false },
        { "id": "contains-duplicate", "title": "Contains Duplicate", "path": "contains-duplicate", "available": false }
      ]
    }
  ]
}
```

### `unit.json`

Each lesson entry records its `id`, `stage`, and `path`, listed in order. The interaction `type` and data live in the lesson's own `lesson.json`.

```json
{
  "id": "two-sum",
  "title": "Two Sum",
  "lessons": [
    { "id": "understand-the-problem", "stage": "Intro", "path": "01-intro/01-understand-the-problem" },
    { "id": "identify-input-output", "stage": "Intro", "path": "01-intro/02-identify-input-output" },
    { "id": "enumerate-pairs", "stage": "BruteForce", "path": "02-brute-force/01-enumerate-pairs" },
    { "id": "find-the-complement", "stage": "Insight", "path": "03-insight/01-find-the-complement" },
    { "id": "build-the-hash-map", "stage": "Optimize", "path": "04-optimize/01-build-the-hash-map" },
    { "id": "compare-complexities", "stage": "Tradeoff", "path": "05-tradeoff/01-compare-complexities" },
    { "id": "spot-complement-problems", "stage": "Recognize", "path": "06-recognize/01-spot-complement-problems" }
  ]
}
```

### `lesson.json`

Lessons are JSON (not Markdown) so the app reads them directly with no parser. The unit lists each lesson with its `stage`; the `lesson.json` declares only its interaction type and interaction data.

`single-choice` example:

```json
{
  "type": "single-choice",
  "prompt": "Which approach finds the pair without checking every pair?",
  "visual": "overview.html",
  "options": [
    { "id": "a", "text": "Check every pair", "visual": "brute.html", "correct": false },
    { "id": "b", "text": "Use a hash map", "visual": "hash.html", "correct": true }
  ],
  "explanation": "A hash map lets you look up the complement in O(1)."
}
```

The remaining lesson shapes are:

- **`info`** → `{ "type": "info", "title": ..., "body": ..., "visual"?: "overview.html" }`
- **`multi-choice`** → like `single-choice`, with multiple options marked `"correct": true`.
- **`order-steps`** → `{ "type": "order-steps", "prompt": ..., "visual"?: "overview.html", "steps": [{ "id", "text", "visual"? }], "answer": [ids in correct order], "explanation": ... }`

### Progress (`localStorage`)

Progress is stored under a single `localStorage` key as a completions map, unit id → array of completed lesson ids:

```json
{
  "completedLessons": {
    "player-sandbox": ["intro-screen", "pick-one", "pick-many", "order-them"]
  }
}
```

Lesson IDs are unique within a unit. There is no progress file on disk; deleting progress is done via the in-app **Reset progress** control.

## Scope of the prototype

Deliver **only two things**:

1. **The pipeline** — the three authoring skills (`extract-spec`, `author-unit`, `author-lesson`).
2. **The vanilla web app** — `app/index.html`, `app/app.js`, `app/styles.css`.

Content shipped in `content/index.json`:

- A small **"Player Sandbox"** fixture unit (`available: true`) whose only job is to exercise the player: it covers all four interaction types plus visualize-on-select and the multi-choice visual-fallback behavior. It uses valid `stage` tags but is **not** bound by the six-stage ladder — it is a dev artifact, not an authored NeetCode unit.
- **Two Sum** and **Contains Duplicate** as `available: false` locked **stubs** only.

**Do not** author the Two Sum unit end-to-end, and do not add other sections, units, app features, or infrastructure.
