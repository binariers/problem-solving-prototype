# Problem-Solving App — Prototype Brief

## The idea

Build a prototype for a **Duolingo-style mobile learning app that teaches problem-solving**. Instead of writing code, the learner progresses by answering small, interactive questions that build understanding of a problem: how to solve it, how to evolve from a brute-force solution to optimized ones, the trade-offs involved, and how to recognize similar problems.

The prototype has two parts:

1. A **content pipeline** that turns a problem (from NeetCode) into structured learning content.
2. A **vanilla web app** that plays that content in a game-like, mobile-first way.

## Vocabulary

- **Section** — a NeetCode topic (e.g. *Arrays & Hashing*), shown as a group of units.
- **Unit** — a single NeetCode problem (e.g. *Two Sum*), authored as an ordered ladder of lessons.
- **Lesson** — one interactive screen inside a unit that teaches or checks a single idea.
- **Supportive visual** — a self-contained interactive `viz.html` attached to a lesson (and, in lessons with options, optionally to individual options), shown to help the learner *see* rather than read.
- **Visualizing area** — the region of the lesson player that hosts the current supportive visual.

## What completing a unit proves

A finished unit must prove three things:

1. The learner **can solve** this particular problem.
2. The learner **understands the technique/pattern** and can recognize similar problems.
3. The learner understands the **evolution from brute force to optimized solutions** and the trade-offs between them.

## Unit structure: the fixed lesson ladder

Every unit is authored as the same ordered ladder of lesson roles:

`Intro → BruteForce → Insight → Optimize → Tradeoff → Recognize`

- **Intro** — understand the problem.
- **BruteForce** — build the naive idea.
- **Insight** — the key realization / pattern.
- **Optimize** — the improved solution.
- **Tradeoff** — compare the solutions.
- **Recognize** — spot sibling problems.

This maps onto the three proofs (Intro+BruteForce → proof 1, Optimize+Tradeoff → proof 3, Recognize → proof 2) and gives the pipeline a stable template to fill and the app a stable sequence to render.

## Interactive lessons

Questions must be **interactive**, favoring seeing over reading. Two rules:

1. **Visualize-on-tap** — a lesson's supportive visual is shown in the visualizing area by default; tapping (not selecting) an answer option that has its own visual loads *that option's* visual in its place, so the learner can explore what the option means before committing.
2. Prefer visualization over text wherever an idea can be shown.

### Interaction types (closed set of four)

The app renders every lesson from a fixed menu of four interaction shapes. Each lesson declares its `type`:

- **`info`** — a teaching screen: title, text, an optional supportive visual, and a Continue button. No question.
- **`single-choice`** — a question with options; tap options to explore their visuals, select exactly one, and the app checks it.
- **`multi-choice`** — like single-choice, but more than one option may be correct; select all that apply.
- **`order-steps`** — several scrambled steps the learner arranges into the correct order (used to test brute-force→optimized reasoning).

### Supportive visuals

- **Every lesson, regardless of type, may declare its own supportive visual**, shown in the visualizing area. This is the primary way a lesson favors seeing over reading.
- **Additionally, in lessons with options** (`single-choice`, `multi-choice`, `order-steps`), each option may carry its **own optional** `viz.html`. Tapping such an option loads that option's visual into the visualizing area in place of the lesson's default (reverting when deselected). Author an option visual only when tapping it reveals something worth seeing; plain options simply select.
- A supportive visual is **fully self-contained** and loaded in a **sandboxed `<iframe>`**. It carries its own interactions and never communicates with the app.
- The app judges correctness **solely from the selected option** (a `correct` flag), never from the visual. Visuals exist only for exploration.
- There is no app-native declarative visual renderer and no message protocol between app and visual.

## Part 1 — the content pipeline

The pipeline is an **offline authoring skill** (a Markdown skill), not a runtime service. It takes a **hand-supplied problem spec** (problem title/slug, statement, and canonical solutions — the problem URL is treated as an identifier, not a fetch target; no live scraping) and emits a **unit folder** named after the problem.

Shape it as a small set of composable skills behind one entry point:

- **`author-unit`** (orchestrator) runs the others in sequence:
  - **`extract-spec`** — normalize the supplied problem into a spec.
  - **`design-ladder`** — produce the six lesson stubs.
  - **`author-lesson`** (per lesson) — write the lesson definition plus any per-option supportive visuals.
  - **`assemble-unit`** — emit `unit.json` and update the top-level content manifest.

All content is **static files committed to the repo**. No runtime LLM calls, no scraping.

## Part 2 — the web app

A **vanilla, zero-dependency, zero-build** app: **one `index.html` + one `app.js` + one `styles.css`**. Open `index.html` and it runs.

- **Mobile-first only** — fixed mobile viewport (max-width ~430px, centered). No desktop view.
- Fetches the content manifest and draws a **Duolingo-style section tree** with locked/unlocked units.
- Opening a unit lazy-loads its `unit.json`, then plays its lessons in order (a **lesson player**).
- A lesson's supportive visual shows in the visualizing area (sandboxed iframe) by default; tapping an option with its own visual swaps it in. Selecting + checking is judged by the app.
- **Progression**: linear unlock — finishing a unit's last lesson unlocks the next unit in the section.
- **Persistence**: progress stored in `localStorage`. No accounts, no backend, no streaks/hearts/XP.

## Content layout

```
content/
  index.json                     ← manifest: sections → ordered units
  two-sum/                       ← a unit folder
    unit.json                    ← unit metadata + ordered lesson list
    01-intro/
      lesson.json
      viz.html                   ← optional supportive visual(s)
    02-brute-force/
      lesson.json
      brute.html
    ...
app/
  index.html
  app.js
  styles.css
```

### `content/index.json`

```json
{
  "sections": [
    {
      "id": "arrays-hashing",
      "title": "Arrays & Hashing",
      "units": [
        { "id": "two-sum", "title": "Two Sum", "path": "two-sum", "locked": false },
        { "id": "contains-duplicate", "title": "Contains Duplicate", "path": "contains-duplicate", "locked": true }
      ]
    }
  ]
}
```

### `unit.json`

```json
{
  "id": "two-sum",
  "title": "Two Sum",
  "lessons": [
    { "id": "intro", "type": "info", "path": "01-intro" },
    { "id": "brute", "type": "single-choice", "path": "02-brute-force" }
  ]
}
```

### `lesson.json`

Lessons are JSON (not Markdown) so the app reads them directly with no parser.

`single-choice` example:

```json
{
  "type": "single-choice",
  "prompt": "Which approach finds the pair without checking every pair?",
  "visual": "overview.html",
  "options": [
    { "id": "a", "text": "Check every pair", "visual": "brute.html", "correct": false },
    { "id": "b", "text": "Use a hash map", "visual": "hash.html", "correct": true }
  ],
  "explanation": "A hash map lets you look up the complement in O(1)."
}
```

Every lesson type may include an optional lesson-level `"visual"` (shown by default in the visualizing area). Other types:

- **`info`** → `{ "type": "info", "title": ..., "body": ..., "visual"?: "viz.html" }`
- **`multi-choice`** → like `single-choice`, with multiple options marked `"correct": true`.
- **`order-steps`** → `{ "type": "order-steps", "prompt": ..., "visual"?: "viz.html", "steps": [{ "id", "text", "visual"? }], "answer": [ids in correct order] }`

Both the lesson-level `visual` and any option/step `visual` are optional; include an option visual only when tapping it reveals something.

## Scope of the prototype

- Author **one full unit end-to-end**: *Arrays & Hashing → Two Sum* (a genuine brute-force → hash-map arc with a real time/space trade-off).
- Optionally include a second node (*Contains Duplicate*) only to demonstrate the section tree.
- Everything else is a locked stub.
